## Mom Test 워크북 — MagicSquare_xx (작성 가이드)

### 페르소나
**누구 한 명**을 말합니다. “학생”, “부모”처럼 넓지 않게, **구체적 상황**까지 적습니다.

| 나쁜 예 | 좋은 예 |
|--------|--------|
| 수학을 어려워하는 사람 | 초등 4학년 자녀(산수·패턴 과목) 숙제를 매일 검사하는 맞벌이 엄마, 주 3회 이상 |
| 퍼즐 좋아하는 유저 | 방과후 수학반(초4) 담당 교사, 시험 전 2주간 연습지·게임 병행 |

**작성 형식 (한 줄~세 줄):**
> [이름/역할], [나이·학년·직업], [언제·어디서 문제가 터지는지], [지금 쓰는 대안]

가설 예시(인터뷰 전):
> 초등 4학년 자녀를 둔 맞벌이 부모. 평일 저녁 숙제 후 “마방진/패턴” 유형 문제에서 자녀가 20분 이상 멈추면 부모가 설명·검산에 개입한다. 지금은 교과서 해설 + 유튜브 검색 + 종이에 직접 그리기.

---

### 인터뷰 답변 (과거 사실)
**의견·미래·칭찬이 아니라**, “마지막으로 그랬을 때”의 **행동·숫자·비용**만 적습니다.

**Mom Test 질문 예:**
- “마방진/패턴 문제로 **가장 최근에** 막혔을 때, 그때 뭐 했어요?”
- “그때 **얼마나** 걸렸어요? 누가 도와줬어요?”
- “그 전에는 **비슷한 문제**를 어떻게 풀었어요?”
- “**돈·시간**을 쓴 적 있나요? (학원, 앱, 책, 프린트)”

**작성 형식 (불릿, 각각 과거형):**
- 지난주 화요일: 3×3 마방진 숙제에서 25분 멈춤 → 엄마가 종이에 숫자 배치 다시 그려줌.
- 지난달: 같은 유형 시험에서 2문제 틀림 → 해설 PDF 인쇄 후 주말에 다시 품.
- 작년: 수학 앱 구독 3개월 했으나 마방진 단원에서는 거의 안 열음(일반 연산만 사용).

**금지:** “앱 있으면 좋겠다”, “AI가 필요해”, “우리 아이는 똑똑해”

### 표면 문제 (금지 — 솔루션 섞인 문장)
인터뷰이가 **말한 말 그대로** 적되, **제품·기능이 섞인 문장**은 여기에만 둡니다. **이 문장으로 제품을 정하지 않습니다.**

표면 문제 예시 (솔루션 섞임 → 이 칸에만):
- “마방진 **앱**이 있으면 좋겠어요.”
- “**AI**가 단계별로 알려줬으면.”
- “**게임**처럼 하면 아이가 할 것 같아요.”
- “**영상**이 없어서 이해가 안 돼요.”

---

### 진짜 문제 (한 문장)
표면 문제에서 **앱·AI·게임·영상**을 빼고, **반복되는 상황 + 원하는 결과(또는 피하고 싶은 손실)**만 남깁니다.

| 표면 | 진짜로 번역 |
|------|------------|
| 마방진 앱이 필요해 | 특정 패턴 문제에서 **혼자 진행을 이어가지 못할 때**, 부모/선생님 개입 없이 **다음 단계로 넘어가는 방법**을 모른다. |
| AI가 알려줬으면 | 설명을 들은 뒤에도 **왜 이 칸에 이 숫자인지**를 스스로 말로 재구성하지 못한다. |
| 게임이면 할 듯 | 연습 분량은 필요하지만 **동기가 금방 떨어져** 정해진 시간만큼 끝내지 못한다. |

**진짜 문제 한 문장 (가설, 검증 필요):**
> 초등 고학년 패턴·마방진 숙제에서, 아이가 한 번 막히면 **스스로 다음 시도를 이어가지 못해** 부모·교사가 **매번 같은 방식으로 다시 설명**해야 한다.

또는 (교사 페르소나 가설):
> 시험 전 2주, 반 학생 중 일부가 마방진 유형에서 **같은 오류를 반복**해 **개별 지도 시간**이 다른 단원보다 길어진다.

- “제출 전 **어떻게** 맞는지 확인했나요? (손계산 / print / 테스트 / 없음)”
- “ECB로 **나눠 본 적**이 있나요? 그때 **어디까지** 했고 **어디서** 멈췄나요?”

**기록 템플릿 (과거형만):**
- [ ] 지난 학기 OOP 과제: 요구사항은 이해했는데 **3일째**에도 `main` 한 파일에 로직 전부 → 제출 직전에만 돌려봄.
- [ ] 이번 주: 4×4 합 34는 손으로 맞췄는데, **빈 칸 2개 코드**는 Row2만 보고 8 넣었다가 **대각선**에서 틀려서 다시 수정.
- [ ] 지난달: AI에 “마방진 풀이 코드” 요청 → **동작은 함** → 시험에서 **왜 그 클래스가 있는지** 설명 못 함.

## 슬라이드와 워크북 연결 (실습 목표 ↔ Mom Test)

| 슬라이드 요소 | Mom Test에서의 의미 |
|---------------|---------------------|
| Entity: `MagicSquare`, `Cell`, `SolveResult` | **무엇이 진실의 상태인지** (그리드·빈 칸·풀이 결과) |
| Control: `SquareValidator`, `MissingFinder`, `Solver` | **규칙 검증·탐색·완성** — “실패 조건 3가지”는 여기서 도출 |
| Boundary: `GridUI`, `InputHandler`, `ResultDisplay` | **사용자 말**이 아니라 **입출력 경계** |
| 실패 조건 3가지 (연습) | 표면 “버그”가 아니라 **도메인 규칙 위반** (예: 합 ≠ 34, 1~16 밖, 중복, 빈 칸 2개 아님, 대각선만 맞고 행은 틀림) |

예시 그리드(슬라이드): Row2 마지막·Row3 세 번째가 `?` → **행/열 합 34로 후보를 구한 뒤** `SquareValidator`로 **대각선·전체 1~16**까지 확인해야 “진짜 문제”(부분 합만 믿기)가 드러납니다.

## Mom Test 결과

**페르소나:**  
4×4 부분 마방진(빈 칸 2개)을 **손·종이**로 풀어보는 **자기주도 학습자**. 과제 마감 없이 **심심해서** 시작할 수 있고, **코드는 열지 않은 채** 후보 숫자를 넣고 차이·합을 반복 확인한다. 맞지 않으면 **처음 칸부터 다시** 검산하다 **수렴하지 않으면 포기**하고 문제를 **다시 열지 않기로** 한다.

**진짜 문제 (한 문장):**  
행·열 합으로 후보를 고르고 넣은 뒤에야 **대각선까지 포함한 전체 제약**이 어긋나면, **손 계산으로 첫 칸부터 전부 다시** 돌려야 해서 **몇 번 반복해도 맞는 조합에 도달하지 못하고** 퍼즐을 **그대로 포기**한다.

**Mom Test 증거 3줄:**
1. **1일 전(같은 문제, 최초 시도):** 될 법한 숫자 → 차이 확인 → 후보 약 3개 × 2칸(같은 방식), 첫 칸 ~10분·둘째 ~5분·전부 확인했으나 **대각선 불일치** 후 **첫 칸부터 재확인 3회**, 끝내 **미완료·포기**, **그대로 둠·다시 보지 않음**.
2. **같은 세션:** **에디터/실행 없이 손만** 사용; **마감·재시도 일정 없음**(심심해서 시작).
3. **3개월 전(다른 문제, 빈 칸 2개):** **대각선을 처음부터** 보며 **끝까지 맞춤** → 같은 유형도 **검증·재시도 비용**에 따라 **완료 vs 포기**가 갈림.

## MagicSquare_1004 세션 3 워크북

### 1) 주제 한 문장 (Mom Test 기반, 솔루션 최소화)

> 4×4 부분 마방진에서 **두 칸을 채울 때**, 행·열 후보만으로 진행하지 않고 **합 34·1~16·대각선 제약을 한 번에 검증**해, 손으로 풀 때처럼 **“끝에서 대각선 틀림 → 처음부터 전부 다시”** 하는 사이클을 **규칙·테스트로 먼저 걸러 낸다**.

---

### 2) R-G-I-O

| | 내용 |
|---|------|
| **Role** | 부분 마방진을 **손으로 시도하는 학습자**의 판단을 대신해, **제약 위반을 즉시 알려 주는** 도메인 규칙·검증 실행 주체 (ECB Control 쪽: `SquareValidator` 등) |
| **Goal** | 빈 칸 2개 상황에서 **후보 조합이 “행만 맞고 대각선은 틀린” 상태**를 **넣기 전·넣은 직후**에 걸러, **전체 재검산 3회 후 포기** 같은 패턴을 **코드·테스트로 재현·차단** |
| **Input** | 4×4 격자(일부 빈 칸), 칸 값 1~16 또는 empty, **목표 합 34** (슬라이드 예시 그리드 포함) |
| **Output** | **통과/실패** + **어떤 제약이 깨졌는지**(행/열/대각/중복/범위/빈 칸 수) — **정답 두 숫자 자동 제시는 이번 세션 목표 아님** |

---

### 3) 성공 기준 3개 (Mom Test 증거와 연결)

1. **대각선 조기 실패 재현:** 인터뷰 증거 ①의 “**대각선이 안 맞음**”을 테스트로 고정 — 행·열은 맞는데 **대각만 틀린** 4×4 입력 1건 이상에서 Validator가 **실패 + 이유=대각**을 반환한다.  
2. **전체 재시작 비용 감소:** 증거 ①의 “**첫 번째부터 다시 확인 3번**”에 대응 — **칸 하나 바꿀 때마다** Rule/Command 한 번으로 **행·열·대각·중복**을 한꺼번에 검사하고, 손 10+5분·3회 재검산을 **수십 ms 이내 동일 입력 재검증**으로 대체 가능함을 Test Loop로 보여준다.  
3. **포기 경로와 무관한 가치:** 증거 ②(마감 없음·다시 안 봄)에 맞춰 — UI·Solver 없이도 **실패 조건 ≥3** (합≠34, 1~16 밖, 중복, 빈 칸≠2, 대각 불일치 등)이 **자동 테스트로 문서화**되어, “심심해서 한 번” 시도도 **다음에 코드 열었을 때** 같은 실수를 반복하지 않게 한다. (증거 ③: 3개월 전 성공 케이스는 **통과 테스트**로 고정)

---

### 4) 표면 문제 — 이번 프로젝트에서 **하지 않을 것**

인터뷰·표면 발화에서 나오기 쉬우나 **Mom Test 진짜 문제와 무관**한 것:

| 하지 않음 | 이유 (인터뷰) |
|-----------|----------------|
| **GUI / GridUI 화려한 시각화** | 실제 행동은 **손만**, 포기 후 **다시 안 열음** — 불편의 핵심은 **표시**가 아니라 **검증 시점** |
| **Solver·자동 채우기·AI 힌트** | “후보 3개 넣기”는 이미 하고 있음; 막힘은 **채우기 부족**이 아니라 **대각선 포함 검증 실패·전체 재검산** |
| **TDD 설교·방법론 과제** | 사용자는 **TDD 제안**이 아니라 **과거 10+5분·3회 재검산·포기** 사실이 증거 |
| **게임화·동기 부여** | 시작 동기 **“심심해서”**, **마감 없음** |
| **완전 자동 정답 앱** | 3개월 전엔 **손으로 완료** 가능 — 이번엔 **규칙 검증·실패 조건**이 우선 |

### 8계층 — **이번 세션에서만** 만드는 것

| 계층 | 이번 세션 범위 (인터뷰·ECB 연결) |
|------|----------------------------------|
| **Rule** | 합 34, 1~16, 중복 없음, 빈 칸 2개, **행·열·두 대각선** — 증거 ① “대각선 불일치”를 **명시적 실패 규칙**으로 |

- 방법: 될 법한 숫자 → **차이 확인** → 후보 약 3개 → **3개 모두 시도**
- 동기: 과제 마감 없이 **심심해서** 시작한 경우 있음
- 실패 시: **다시 열지 않기로** 하는 경우 있음

## 4. Real Problem (One Sentence)

행·열 차이로 후보를 골라 칸에 넣고 손으로 다시 계산해 확인하는 과정에서, **대각선까지 포함한 판정이 늦게 드러나** 첫 칸부터 전부 다시 검산을 여러 번 반복해도 맞는 조합에 도달하지 못해, **확인 비용만 쌓인 뒤 미완료로 중단**한다.

## 6. Mom Test Evidence (Quoted)

1. “1일전이었고 될법한 숫자를 한번 넣어서 답과 얼마나 차이가 나는지 확인했어”

3. “**10분**” / “**5분** 다 확인 했어” / “**다 계산해야해서 시간이 오래 걸렸어**” / “**손으로 했어**”

**보완 질문 (미회수):** “5분 확인” 시 **10선(행4+열4+대각2) 전부** vs **대각만 나중** — 채점 시 −1, 추가 인터뷰 권장.

## 2. Problem Statement

### 2.1 진짜 문제

행·열 차이로 후보를 골라 칸에 넣고 손으로 다시 계산해 확인하는 과정에서, 대각선까지 포함한 판정이 늦게 드러나 첫 칸부터 전부 다시 검산을 여러 번 반복해도 맞는 조합에 도달하지 못해, 확인 비용만 쌓인 뒤 미완료로 중단한다.

### 2.2 표면 문제 (Out of Scope)

| Out of Scope | 이유 |
|--------------|------|
| 자동 풀이 / Solver 프로그램 | 후보 시도는 이미 함; 막힘은 채우기가 아닌 판정 |
| Validator·GUI 앱 | 실제 행동은 손만; 포기 후 재방문 없음 |
| UX·게임화·AI 힌트 | 증거는 분·재검산 횟수 |
| 정답 두 칸 자동 출력 | 세션 3 목표는 판정·실패 조건 |

## 5. Functional Requirements (Session 3)

### 5.1 Rule

- R1: 각 **행** 합 = 34 (완성된 행만 또는 부분 허용 정책 명시)
- R2: 각 **열** 합 = 34
- R3: **대각선 2개** 합 = 34
- R4: 값 ∈ {1..16}, **중복 없음** (0 제외)
- R5: **빈 칸(0) 정확히 2개**

### 5.2 Command

- C1: `validate_grid(grid) -> ValidationResult`
- C2: `validate_after_place(grid, row, col, value) -> ValidationResult`

### 5.3 (Optional) Skill

- S1: `check_candidates(grid, candidates[]) -> ValidationResult[]` — 행·열만 보고 넣기 **전** 10선 일괄 검사

### 5.4 Test Loop

- T1: Red — 대각-only FAIL fixture 1건
- T2: Green — Rule/Command 구현
- T3: Refactor — 실패 조건 ≥3 명명·문서화
- T4: Regression — 통과 격자 1건 (3개월 전 성공 유형 대응)

## 6. Non-Functional Requirements

- **재현성:** 동일 격자 입력 → 동일 Pass/Fail (손 3회 재검산과 동일 판정)
- **비용:** 1회 검증 << 손 10분+5분 (개발 환경 기준 ms 단위)
- **테스트 우선:** UI 없이 CLI/단위 테스트만으로 성공 기준 충족
